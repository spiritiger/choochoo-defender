## v0.6.10：十字直行优先 + 相接口径两处收窄

大王两条：① 火车遇十字应优先直行；② 质问「为什么条件变成 1 格相邻也可以清理了」（附 KDG-MAP 数据）。

### ① 十字直行优先（`js/state.js`）
- 新增 `GS.straightenRing(ring)`：十字格的"进边 → 出边"配对决定列车是直穿还是拐弯。
  每个十字 3 种配对（对角互配 or 两种拐弯），最多 3^6=729 种组合全枚举，
  取「仍是单环 + 拐弯最少」的方案；环长与格子集合完全不变（同一条边集，只改走法）。
- 新增 `GS.countTurns(ring)`：统计"拐弯通过"次数（供测试与探针）。
- **关键实测结论**（300 张固定种子盘面 + 独立实现穷举交叉验证）：
  「直行优先」在实际盘面上**不改变任何结果** —— 能直行的十字（86 张含十字里约 39 张）
  本来就直行；剩下的是 **8 字形相切**（直行配对会把单环劈成两条环，是数学必然），只能拐弯。
  且这些十字本身必需：把搜索限制成"每格最多走一次"后，即使把预算从 120ms 放大到 **4000ms**，
  47/47 张仍找不到无十字的环 → 「让环绕开十字来实现直行」这条路走不通。
  （中途试过 `solveOnRegion(..., noCross)` 参数 + 无十字替代搜索，验证无效后**已整体删除**，
  只保留最优选择器，保持代码精简。）
- `test_rail [9]` 增加断言：斜切角盘面的十字是直穿（拐弯数 0）。

### ② 相接口径两处收窄（`js/engine.js`，回答大王的第 2 问）
根因有两个，都在"相接"的计算口径上：
- **旧口径 A（真 bug）**：形状**自身压住的已有空地**也算作相接 → "大半压在空地上、
  只探出 1 格"的形状也能过。大王盘面里 (1,10)/(3,10)/(1,6) 这些"只 1 个区域邻居"的格
  正是这么来的（3×2 形状压住 row9 三格、只往 row10 探出一行）。
  → 改为**只数形状外圈的邻格**。
- **旧口径 B（豁免过宽）**：只要"形状或它的 4 向邻格挨着内区"就豁免 2 格要求 →
  内区旁边一大片都能少格相接。→ 收窄为**形状必须真的压住内区格**（贴着内区角往外长仍可）。
- 拒绝文案改「需与区域相邻 2 格（或压住内区）」；`ui.js` 卡面 meta、`renderer.js` 预览同步。
- 附：盘面里"只剩 1 个区域邻居"的格子，第二邻居都是**金币格**（(1,7)/(2,10)）——
  金币不算区域，视觉上就成了"1 格相邻"。这是金币规则与相邻规则的交互，已在文档写明。

## v0.6.11：三选一卡牌去重

大王：「请在选项中去重，我发现偶尔会出现三个一样的形状选项」。

**根因**：形状只有 3 个尺寸家族（`CFG.SHAPE_SIZES=[4,6,8]`，每档一种矩形），
而 `nextOffer` 原本是 `[pickShapeCard(), pickCard(), pickCard()]` 三张**独立随机**，
所以三张同形状的概率约 2%（"偶尔"）。

**实现**（`js/state.js`）：
- 新增 `GS.buildOffer()`：① 先摇牌型 —— 每张 30% 概率是经济建筑（沿用旧概率），
  但经济卡**最多一张**；② 形状档位 Fisher-Yates 洗牌后依次发放，**每张卡的尺寸家族都不同**
  （因为每档只有一种矩形，等价于"三档面积不重复"）；③ 位置打散，首位保持形状卡（旧体感）。
- 新增 `GS.cardSig(card)`：去重规则的可执行定义。形状按**外框两维排序后**做签名
  （即 **2×3 与 3×2 视为同一形状**，旋转也算重），经济卡固定 `'econ'`。
- `CFG.randomShape(size)` 支持指定面积档（发牌时用）；`GS.pickCard()` 已无用**删除**。
- **设计取舍**：刻意不用"抽重了就重抽"的拒绝采样 —— 那样会把经济卡出现率从 51% 抬到 73%；
  现在的做法经济卡出现率 50.4%，与旧版 51% 基本一致，且无任何重试循环。

**验证**：探针 probe_offer_dedup.js **5/0**（3 万组三选一）：选项数恒 3、
签名两两不重复 0 违规、形状家族不重、经济卡最多一张、首位恒为形状卡；
分布 2×2/2×3/2×4 各约 27.7%、经济卡 16.8%（50.4% 的组合含一张经济卡）。
`test_rail` 24/0、`test_rules` 14/0。文档 §清理工具 已补「卡牌去重」小节。

## ⚠️ 重要教训：探针的"度量口径"本身会骗人（`probe_straight_cross`）

`probe_straight_cross.js` 里那条 `整理后的拐弯数 == 穷举最优` 断言**长期是假的**，本轮拆穿：

- **现象**：偶发 FAIL（1/12、2/11…），报"实现=4 穷举最优=2"。加大采样后是 **53/53 全部非最优**，
  甚至有"只有 1 个十字却报 turnCount=21"的盘面 —— 这不可能。
- **根因（两个函数根本不是同一个量）**：
  - `turnCount(ring)`：遍历**度数 ≥2 的格**（含十字），数每一次"经过"的进边/出边**不是对边**的次数
    → = **整条环里拐弯通行的总次数**（普通 90° 拐弯也算）。
  - `bruteBest(ring)`：只处理**恰好被走两次的格**，数某个配对方案下 `isOpp(A,B,X)` 为假的**配对数**
    → = **单个十字有几种配对不算直穿**（最大值 2）。
  - 一个数"全程拐弯"，一个数"单格配对数"，**量纲不同，本来就不可比**。
- **为什么以前"看起来能过"**：原采样条件 `if (!cc2 || turnCount(rr) === 0) continue` 把
  「实现已全直行（拐弯数 0）」的盘面全部跳过 —— 而定为 0 的期望值本来就是 0，本该 PASS。
  于是只抽查"仍带拐弯"的少数盘面，偶尔蒙对。
- **处理**：删除 `bruteBest` 整段（含 `PAIRS_LOCAL`、`isOpp` 的探针副本），换成
  `straightenByBrute(ring)` —— **同一个 `turnCount` 度量**下、独立枚举十字配对走法取最优。
  新断言抽查 17 张含十字盘面全部一致，连跑 5 次稳定 ALL OK。
- **可复用的铁律**：**写"A/B 对照"或"最优性"断言前，先确认两边数的是同一个量**。
  差一个量纲（"全程次数" vs "单点个数"）就会得到 100% 假失败，而这类失败很容易被
  "改成更宽松的断言"掩盖过去 —— 那等于把回归测试的看门能力删掉。

### 桩化 DOM 的坑

无头跑 `file://` 版游戏时，DOM 桩要备齐这些容易被忘的方法：
`insertAdjacentHTML`（`UI.renderCards` 用它插卡片）、`append`、`remove`、`cloneNode`、
`replaceChildren`、以及 `canvas.getContext('2d')` 的完整绘图方法表。缺一个就报
`xxx is not a function` —— **注意区分是"桩缺方法"还是"真 bug"**，前者补桩即可。

## v0.6.16：生成期直行优先（`closedTrail` DFS 选边）

大王（附 KDG-MAP，#10 盘面 rail 72）：「**铁轨的生成**，能不能优先走直线而非十字？
虽然路径长度是一样，但是视觉观感不一样」。

⚠️ **先纠正一处理解偏差**：我第一轮以为是"事后把已生成的环掰直"，去挖 `straightenRing`

不是事后重排。这个区别决定了改动位置：**`closedTrail` 的 DFS**，而不是 `straightenRing`。

### 挖到底的旧结论（先排除"是不是求解器选错了"）

**① 243 种组合穷举 → 大王那张盘面的拐弯改不动**
5 个十字（`(6,1)(6,2)(4,10)(4,11)(1,8)`）× 3 种配对 = 3^5 = **243 种**，
**只有 1 种能连成单环**，它的拐弯数正好是 **2** —— 就是求解器原本给的。
（逐个十字实测：直行 8 / 拐弯 2，直行率 80%；问题只在 `(4,10)`，两次通行都拐。）

**② "零拐弯"与"大环"互斥**（40 万次随机采样）
| 拐弯数 | 可达最长环长 |
|---|---|
| 0 次 | **36 格**（近矩形） |
| 2 次 | **72 格**（当前） |
原因：`(4,10)` 是**竖脖子双结**（r10/r11 的 c4 各走两次，c5 在 r9/r12 是废墟，
只剩 c4 一根脖子贯穿）→ 两个结的配对被互相锁死。**"全程直线"和"围着地盘绕大圈"互斥。**

**③ 度数分析**：可用区域里 18 个"度 2 且两邻居相邻"的角格（如 `(6,0)` 邻 `(7,0)`/`(6,1)`），
但都在角落、未必被环经过；`(4,10)` 是**度 4**（标准十字），它的拐弯来自**全局拓扑**而非地形死角。

### 实现（`js/state.js` 的 `closedTrail`）

在 `dfs(cur)` 里：算出**来路方向**（`cur - path[path.length-2]`）→ 求"直行边"
（邻居 = `cur + (cur-from)`，即两格之差互为反向）→ 把候选边分两轮试：
```js
for (var pass = 0; pass < 2; pass++) {
for (t2 = 0; t2 < cnt; t2++) {
  if (wantIdx >= 0) {
    var isWant = (t2 === wantIdx);
    if (pass === 0 && !isWant) continue;   // 第一轮只试直行边
    if (pass === 1 && isWant) continue;    // 第二轮试其余
  } else if (pass === 1) break;            // 无直行边 → 只跑一轮
  ...
```
- ⚠️ **只改试边顺序，不动任何可行性判定**（`vis`/`usedEdge`/`needLeft`/三道 BFS 剪枝全原样）
  → 解一定找得到、**环长与格子集合不变**、结果仍可复现（顺序是确定性的）。
- 起点无来路（`path.length === 1`）→ `fromId = -1`，不做区分，按原顺序试。
- `isTwice`/`w`/`e1` 每次迭代开头都重新赋值，**两轮之间无状态污染**（已逐行核对）。

### 验证（同种子、OFF=原顺序 vs ON=直行优先，两版面对**完全相同的盘面序列**）

| 指标 | OFF | ON |
|---|---|---|
| 十字直行率 | **34.2%** | **100.0%** |
| 平均环长 | 15.6 | **15.6（一模一样）** |
| 环序列不同的盘面 | — | 50/300（走法变了） |
| **格子集合不同的盘面** | — | **0 张** |
| **环长不同的盘面** | — | **0 张** |
| **十字位置不同的盘面** | — | **0 张** |

**400 张安全性验证**：环长变短 0、格子数变少 0、**轮廓覆盖变少 0**（400 张覆盖数全相同）。
→ 恰是大王要的"**路径长度一样、视觉观感不一样**"。

**对大王那张盘面不生效**（正确行为）：`(4,10)` 仍是 2 次拐弯、环序列逐格未变 ——
因为它是 243 种里唯一可行的解，**没得选**。直行优先只在"有得选"时生效。

## 十字能否消掉（同日第二轮，大王又报一例）

大王贴 `rail(56)` 盘面（`KDG-MAP v1 2026-09-23T10:26:42`）：「怎么还是有没必要的十字」。
**又是他说得对、我又判断错了。**

### 盘面事实
- 复现**逐格一致**：步数 56 / 格数 53 / 十字 3 → `(3,2) (1,6) (2,2)`。
- 轮廓 42 格 / 补格候选 20 格 / A = B∪H 共 62 格，`rank = 91 − 62 + 1 = 30`。

### 我第一轮的错误结论（已推翻）
我做了两件事就下了"3 十字是几何必然"的结论：
1. `sample3.js`：打乱候选边顺序采样 400 次 → **400/400 都是 3 十字、位置一模一样**；
2. `hlimit.js`：逐档穷举 `hLimit × maxVisit`（漏了 `tol`！）→ 只有 hLimit≥11 才有解，且最少 3 十字。

**两件事都不足以证明"必然"**，因为：
- 采样 400 次的**自由度维度搞错了** —— 打乱试边顺序**不改起点**（起点写死 `Bl[0]`），
  搜索树的入口固定，同一入口里换顺序只能换到 3/4 十字那两类；
- 逐档穷举只覆盖"**给定起点**下 DFS 能撞到的解"，不是全局最优。

### 决定性实验（`enum2.js` / `enum3.js`）
在 A 内**穷举所有合法欧拉环**（每格 ≤2 次、每边 ≤1 次、围住核心），7000 万节点、
632674 个去重环，记录"覆盖轮廓格数 vs 十字数"：
- 覆盖 ≥42（不缩水）的解共 **208 个**；
- **其中十字=1 的有 11 个**（格数从 53 到 57 都有）、**十字=2 的有若干**；
- ⇒ **存在「覆盖 42 不缩水 + 十字 2 + 格数 54」的解**，十字只剩 `(1,6)` `(3,3)`。

### 根因（真 bug）
`js/state.js` 的 `closedTrail` 里：
```js
var start = Bl[0];     // 恒取"最上最左"的轮廓格
```
遍历 42 个轮廓格逐个当起点（`start.js`），同一 `hLimit=12` 档产出：
| 起点 | 产出 |
|---|---|
| `(0,3)` `(1,3)` `(2,3)` 共 3 个 | **2 十字** |
| `(2,0)` 等 14 个（含 `Bl[0]`） | 3 十字（现状） |
| 其余 25 个 | 4 十字 |

`Bl[0]=(2,0)` 恰好落在"3 十字"那一类。**枚举路兜底也没救**：`rank=30 > RANK_CAP=19` → null。

### ✅【已实施 v0.6.19】多起点择优（"起点写死"的真 bug 修掉了）
大王原话链：「胡说，最上面的两个十字是不必要的，你再检查下，看看为什么」
→「这两个方案的区别是什么」→「**直接做，不评估了**」（跳过影响面评估，直接落方案甲）。

**改了什么（`js/state.js` 三处）**
1. `closedTrail(...)` 签名末尾新增 **`startIdx`**；起点行改为
   `var start = (startIdx >= 0 && startIdx < Bl.length) ? Bl[startIdx] : Bl[0];`（向后兼容）。
2. 新增常量 **`START_TRIES = 9`**（"五个上限"之一）。9 是**实测拐点**：大王那张盘 42 个起点里
   只有 3 个（si=8/9/10，即 `(0,3)(1,3)(2,3)`）能出十字 1，前 9 个恰好覆盖；加到 12 只多花
   ~200ms、结果不变。
3. `solveOnRegion` 重构为**两阶段**：
   - **① 定档**：`si=0` 走一遍递升 `hLimit` 阶梯，首个命中档即 `k*`（一步**定死**档位）；
   - **② 择优**：只在 `k*` 档上跑其余起点，按三级字典序（覆盖 → 十字 → 格数）择优，
     命中 **`bestCross === 0` 立刻早停**。

**⚠️ 两次翻车（都记进 `docs/铁轨bug诊断-001.md §14`）**
| 版本 | 做法 | 结果 |
|---|---|---|
| 第一版 | 起点塞进 `ki` 档内部 + 与阶梯**共用**预算 | `hLimit=0..9` 十二起点烧掉 945,230 节点（63%），唯一有解的 `hLimit=11` 没跑到 → **反退化 4 十字 / 2471ms** |
| 第二版 | 每起点各跑**完整**阶梯 + 各自独立预算 | 单起点 15~47 万节点 × 12 = 300~560 万，**远超 150 万** 节点预算 |
| 最终版 | 两阶段（定档一次 + 最优档多起点） | 十字 1 ✓ |

**总根源**：**补格阶梯的"失败证明"是指数阶**（`hLimit` 0→9 档消耗 84 → 590,613 节点，约 ×2.5/档）。
所以"定档"必须只做一次，不能每个起点都从头爬一遍。

**另两个实验结论**
- `desc=true` 定档更差（十字 4：大补格档下所有起点都差）⇒ **递升定档不可替代**。
- 写死顺序 vs 多起点的差别不是"运气"：`Bl[0]=(2,0)` 恰好落在 3 十字那一类。

**验收**

- `test_rail **35/0**`（新增 [12] 起点敏感盘）、`test_rules **16/0**`、`test_build **8/8 PASS**`。
- **零退化证明**：440 张固定种子盘（200 随机 + 240 大轮廓）逐盘对比 →
  **十字数改善 0 / 持平 440 / 退化 0**；耗时 4.1→4.3ms、53.0→53.2ms（噪声内）。
- **反向断言有效**：把 `START_TRIES` 改成 1，[12] 立刻失败并复现 `1,6 2,2 3,2` ⇒ 该用例不是"恒过"。

### ⏳【待大王拍板】①级墙钟 400ms → 700ms？
多起点择优把①级计算量抬了几倍，**真实墙钟**下会被掐断：
`400ms` / `500ms` → 退回十字 3（= 旧行为）；`600ms` 临界不稳；`700ms+` 才稳定十字 1。
代价：极端盘面清理后重算 ~0.2s → ~0.65s。
**在拍板前如实保持 400ms**（宁可少消十字，也不擅自给大王加卡顿）。

### 方法论（本轮新增，值得记）
- **"随机化采样"采不到的东西 ≠ 不存在** —— 采样前先想清楚**自由度有几个维度**。
  本轮打乱了"试边顺序"却没动"起点"，采的其实是同一个入口下的解，白跑 400 次。
- **"逐档穷举参数"也未必是全局最优** —— `hLimit × maxVisit` 穷举漏了 `tol`，
  且每一档内部仍是"给定起点下 DFS 先命中先返回"，覆盖不到起点维度。
- **要证"必然"就得真穷举** —— 本轮的 `enum3.js`（枚举 A 内所有合法环）才是一锤定音的那个实验。
- 分工：**采样用来证"存在"（找到即算数），穷举用来证"不存在"（必须穷尽）**。
  我上轮把采样当成了"不存在"的证据，这是逻辑错误。
- **（v0.6.19 补充）"改成多起点试"必须回答预算从哪来** —— 补格阶梯的失败证明是指数阶，
  多起点 × 完整阶梯 = 预算爆炸。正解是**先把档位定死（跑一次阶梯），再在那一档上换起点**。
- **（v0.6.19 补充）加优化维度前先量基准** —— 440 张固定种子盘逐盘 A/B（不是抽样、不是 `Math.random()`）
  才敢说"零退化"。
