## 哐当哐当守卫战（kuangdang-guard）代码解析 + 本地跑通

**项目性质**：免构建纯静态小游戏。`index.html` + 7 个经典脚本（非 ES module）+ 1 个 CSS，`file://` 直开即可。
逻辑画布 390×844，地图 11 列 ×15 行；HUD(52px) 与底部面板(232px) 是 HTML，画布只占中间 560px。

**架构**：`config/map.js`(常量/布局/俄罗斯方块形状) → `state.js`(状态 + 铁轨环生成，最重的模块) →
`transport.js`(贴轨经济建筑发钱) → `engine.js`(清理/建造/列车) → `renderer.js`(Canvas 绘制) →
`ui.js`(HUD/三选一牌/点击) → `main.js`(引导 + rAF 主循环)。
`test_rail.js` 是 cscript/JScript 的脱机调试工装（铁轨外形算法压测），不是游戏运行时的一部分。
`docs/设计规格.md` 是 v0.3 设计稿，描述的是完整版（昼夜/塔防/10 夜），当前代码只实现了"白天清理 + 经济建筑 + 列车跑圈收钱"的迷你演示子集。

**核心机制**：铁轨不是预铺的固定环，而是**每次地图变化后按"围绕连通镇中心的已清空空白区的外轮廓"重新生成**一条正交闭环。
所以铁轨会随着玩家清理废墟 / 建造而动态改变形状；列车沿 `GS.railPath` 逐格前进，经过贴轨经济建筑即 +6 金币。
经济建筑必须「已清空 + 紧贴铁轨」才能建。三选一抽牌每次扣 15 金币（`GS.offerCost`）。

### 修掉的 P0 死循环（致命）
`js/state.js` 的 `GS.cutDoubledEdges`（剪除铁轨往返边）**在约 15%~20% 的随机地图上无限震荡**：
- 根因：`cutB` 的索引构造写成 `cells[0..i] + cells[j+1..n-1]`，把 `cells[j+1..i]` 保留了两遍，
  剪枝后长度变成 `n+(i-j)`、比原环还长 → 在 24↔36 两个状态间来回跳，`changed` 永远为 true，主线程死锁（页面白屏）。
- 修法：`cutB` 改为只保留弧1 `cells[j+1..i]`；加 `if (pick.length >= cells.length) break`（剪枝必须严格变短）；
  while 加 `guard++ < 500`。
- 验证：原死锁样本（mulberry32(13)）从永久卡死 → 1ms 完成；1000 次开局从卡死 → 0.36s 全过。

### 顺手修的两处笔误
- `css/style.css`：`#hudGold .hud-val` 是后代选择器，而 `#hudGold` 本身就是那个 `.hud-val` span → 规则永不命中，金币数字不变金。改为 `#hudGold`。
- `js/ui.js` 的 `UI.pickCard`：`GS.status = ''` 写到了不存在的字段，提示文案不会被清掉 → 改为 `UI.setStatus('')`。

### 已知残留瑕疵（未改，属算法能力边界，作者注释里已承认"宁可留少见对角"）
对照实验（固定 500 种子）：跳过 `cutDoubledEdges` 时跳格 123 例/斜线 206 例/重复格 335 例；
调用后降到 跳格 6 / 斜线 9 / 重复格 21。即该函数是有益的，残留的是它能力边界：
- 45° 斜线步（railPath 里相邻两格对角）→ 列车会走斜线、渲染靠借角拆 L，两角皆废墟时断笔。
- 跨格跳变 d>2（1.2% 开局）→ 列车瞬移 + 铁轨画出一条跨格直线。
- 零长度重复格 d==0（4.2% 开局）→ 无害，但说明去重没覆盖环的收尾接缝（`trimOutlineNeedles` 的 merge 不处理 last↔first）。

## 第二轮：铁轨「重叠 + 斜线」根因定位与重写（state.js 铁轨算法整体替换）

**用户反馈**：截图中铁轨出现错误重叠，且列车被画成 45° 斜线。

**像素级取证方法**（值得复用）：用 Pillow 在截图里先按地形色精确定位地图包围盒 → 反推 `LAY`（原点 630,94、格宽 36.11px）→
再沿相邻格中心的连线中点采样铁轨色 `#7a8090` → 把「实际画出来的铁轨」还原成格子图并统计度数。
结论：10 个铁轨格、12 条边、其中 4 个格度数为 3、独立回路数 3。**根本不是单条闭环，而是三环串联的自相接触结构。**

**统一根因（两个症状同一个原因）**：原实现用「贴着已清空区轮廓走」的轮廓法生成铁轨，但该方法在**格心表示**下先天无法保证简单闭环。
当清空区只有 1~2 格宽或有凹角阶梯时，那一圈边界格在 4-邻接下**不存在哈密顿环**（凹角格的两个邻居本身已是它的必经邻居，
一旦取用就提前闭合，其余格子再也接不进来）。于是轮廓必在凹角处自相接触：
- 同一格被走两次 → 度数为 3/4 的交叉点 = 画面上的「铁轨重叠」；
- 凹角两侧都是废墟、无空白格可补桥 → `smoothDiagonals` 拒绝压废墟、`stripResidualDiagonals` 无法就地修复
  → 残留对角步 = 列车被旋转 45° 的「实际斜线」。

复现证据：无头环境下模拟随机游玩，**清 1 格废墟就会触发**（seed=0/1/2 各一步即出度数 3/4 或格重复）。
原 `recomputeRails` 的 `orthoOk` 校验只查「每步正交 + 无重复无向边」，**漏掉了"是否简单闭环"**，所以坏路径被放行。

**修复方案**：把铁轨改成 **「包含镇中心、向外生长到的最大可行矩形闭环」**，整块替换 `GS.recomputeRails`，
删除 8 个相关辅助函数（`buildOutline / stripResidualDiagonals / smoothDiagonals / trimOutlineNeedles /
cutDoubledEdges / pruneDeadEnds / buildRing / buildRailPath`）。state.js 从 511 行降到 193 行。

实现要点：
- `ringOk(c0,r0,c1,r1)`：矩形四边全部是「空白且无建筑」的格，且至少 3x3（镇中心建筑物天然不可能落在四边上，故无需额外判中心在内）。
- 常规路径：沿用上次的 `GS.railRect`（环上不会被放建筑 → 永远保持合法）只做单边贪心扩张，**O(周长)、0.0102ms/次**。
- 兜底路径：`GS.railRect` 缺失或失效时，全量扫描所有含镇中心的矩形取最大者（2300 候选，仅开局走一次）。
- 顺时针输出周长格序列。每格恰好 2 个铁轨邻居 → **由构造保证**是单条简单闭环。

**踩过的坑（重要）**：第一版把兜底起点写死成「镇中心 3x3 最小环」，结果玩家在环内侧合法建了一栋经济建筑后，
3x3 环失效 → 铁轨被清空（224/400 局中招）。必须「沿用当前矩形」或「全量取最大」，不能退回固定尺寸。

**验证结果**：
- 200 局 × 80 步 = 16000 次操作：非法铁轨 **0**、铁轨缩短 **0**（单调不缩）。
- 端到端 12000 帧：列车角度偏离正交 **0.0000°**、错误 0。
- 抓 renderer 真实 `moveTo/lineTo` 指令：斜线段 **0**、断笔 **0**、最长段 **1.00 格**、闭环 **闭合**。
- 「清空外一圈」→ 环长大一圈：14→20→24→28→32，全部合法（与设计规格 §2 的同心环一致）。

**回退点**：`.workbuddy/backup/state.js.before-rail-rewrite`（完整原文件）。

**注意的设计取舍**：贴轨建造时若把建筑盖在「未来可能扩张的那一圈」上，会永久挡住该方向的扩张（因为环外扩要求整边全为空白）。
这是有意保留的规划取舍；若觉得太苛刻，可改成只允许在铁轨内侧建造。

## 第四轮：铁轨改成「不规则闭环」（用户手绘红线为基准）

**用户给的规则（三条，已确认）**：
1. 形状是**不规则闭环**，贴着已清空的空白区走，不再强求矩形（规格 §2 的「向外/向内各退一圈」失去基准，需一并重写）。
2. 凸出门槛是**能凸就凸**：只要空白格允许，就把某条边上的「任意连续一段」整体往外推一格，允许推成台阶。
3. 碰到会形成 **1 格宽细脖子**的地方，**那个方向就不凸**（校验不过就跳过，绝不硬来）。

**关键结论：用户那张红线截图拍的是「上一版矩形算法」的页面，不是新代码。** 硬证据三条：
- 截图里铁轨是 c4..c6 × r6..r9 的 3×4 矩形（周长 10），正是「含镇中心最大面积矩形」的首个命中者（面积 12）。
- 金币 = 120 = 开局值；4 栋经济建筑位置 = `placeEconInit(4)` 的产物 → 是**开局未动过**的状态。
- 把截图地形原样喂给新算法，输出是 **14 格不规则环**（外接 c3..c7 × r6..r9），不是那个矩形。
→ 结论：用户只是没刷新；新算法在同一地形上本来就会往 c3（左）、c7（右）凸出去。

**像素取证流水线（本轮新增，比上一轮更稳，值得复用）**：
1. 标定：`CELL / OX / OY` 每张截图都不同（本轮是 36.5 / 41.75 / 110.75；上一轮那张是 36.11 / 630 / 94）。
   最稳的锚点是把**灰色铁轨矩形**当尺子（它必是「含镇中心的矩形环」），用它的包围盒反推。
2. 地形：逐格在格心 0.3~0.7 范围内采样 6×6 点，按色投票 blank / rubble / econ / core。
   ⚠ 建筑图标里有红/橙色像素 → 会把格心判成 core 或污染红线检测，要按格子整体投票而不是单点判定。
3. **把用户手绘的红线还原成格子区域，最稳的做法是「泛洪填充」而不是「描线」**：
   红线当墙（要膨胀 3px 补手绘断缝），从地图四角 BFS，没被淹到的格 = 被围住的区域；
   该区域的**边界层**就是用户想画的环。逐格求「格心到红线像素的最短距离矩阵」只能当辅助参考
   （手绘线不贴格心，用距离阈值必然要么漏要么糊）。
4. 再把还原出的环与算法输出做逐格 diff。

**本轮实测的差异与归属**：
- 新算法输出 14 格：`(3,7)(3,8)(3,9)(4,9)(5,9)(6,9)(6,8)(7,8)(7,7)(7,6)(6,6)(5,6)(4,6)(4,7)`。
- 用户红线想多要一个**顶部凸包**（r5 的 c5/c6）。该凸包做不出来，原因二选一都需要一个废墟格：
  走 `pushRing` 台阶要 (4,5)，走「保两端、抬中间」的凸包要 (7,5)，两格在截图地形里**都是废墟**。
- 这不是 bug，正是用户第 3 条规则「细脖子的方向不凸」的直接后果。

**实现**：`GS.recomputeRails` 重写为「校验驱动的贪心外推」（state.js 193 → 270 行）：
- 起点先扫描「含镇中心的最大合法矩形环」；此后**沿用上次的环**（只外推不外收 → 单调不缩、不会在眼前跳来跳去）。
- `tryPush`：按 `k` 从长到短遍历每条直边上的连续段、两个垂直法线各试一次；
  用 `pushRing`（段整体外移一格 + 两端补台阶）生成候选，用 `ringOk` + `insideRing(core)` 把关。
- `ringOk` 是唯一防线，四条缺一不可：格不重复 / 全部为「空白且无建筑」/ 相邻两步严格正交 / **每格度数恰为 2**。
  度数 != 2 就是重叠（交叉点），必须拒绝。
- 外推必须严格增加、绝不内收；循环加 `guard < 300` 上限。

**做过又回退的实验（记下来避免以后重复踩）**：给 `tryPush` 加第二类候选 `bumpRing`（段两端原地保留、
段内抬起 = 「凸包」画法）。对照 400 局结果：**形状分布完全一致（唯一形状数都是 91）、非法都是 0，但耗时 +52%**
→ 该类候选在所有情况下都排在 `pushRing` 之后、且 `pushRing` 总能命中，属**死代码**，已回退。
教训：加算法分支必须做「开关对照实验」验证它真的会被选中，不能凭直觉加。

**第四轮验证数据（全部绿）**：
- 400 局 × 60 步 = **24000 次重算**：非法铁轨 **0**、环面积缩小 **0**、空铁轨 **0**。
- 随清理而长大的对局 **242/400**；开局环长分布：8×166 10×106 12×55 14×39 16×18 18×8 20×4 22×1 24×2 30×1。
- 端到端：错误 0、列车角度偏离正交 0。
- renderer 真实绘制指令（环长 10 / 22 / 30）：斜线段 **0**、断笔 **0**、最长段 **1.00 格**、闭合。
- `railRect` 已确认**只在 state.js 内部使用**（外部无人引用），降级为调试/外接参考，不再是形状基准。

**仍存在、需用户拍板的设计取舍**：外扩要求「某侧整条边/整段全空白」，所以把经济建筑盖在「未来要长出去的那一圈」上
会永久封死该方向。可选改法：只允许在铁轨内侧建造。

**画布旁注**：预览用的零依赖 Node 静态服务仍在 `http://127.0.0.1:5173/`（后台任务，改动后需刷新页面）。

## 第五轮：确认「铁轨不凸 = 地还没清」并锁定选项 1（本轮代码零改动）

**用户拍板**：第四轮给的三个选项里选 **1 —— 铁轨只走已清空格**（不允许压废墟、不放开细脖子）。
→ 本轮**不改任何代码**。`js/state.js` 仍 270 行（mtime `07:35:16`，与第四轮替换后一致），项目根仍为 `.workbuddy css docs index.html js`。

**新增验证手法：反事实归因测试（`growth.js`）** —— 专门把「不是 bug，只是前置条件没满足」和「真是 bug」分开。
- 只走公开 API：对每局最终环上每一格的**每个外法线方向**枚举「k=1 外推」候选；把挡住它的格子清成 `blank`，
  重新调用 `GS.recomputeRails()`，再看 `GS.railSet` 是否吃进了那个候选位置。**不复制 state.js 内部闭包**（避免测试与实现漂移）。
- 前置过滤：射线法判内/外（1695 处法线指内，跳过）、越界 4 处跳过。
- **挡路的是「建筑」的 307 处单独计数并排除** —— 那是第四轮记下的设计取舍（建筑封死扩张方向），不属于「清废墟就能长」。

**结果（200 局 / 2505 个候选位置）**：
- 2198 处挡路的是废墟。其中 **274 处实为「三格已空却仍不凸」**（细脖子情形）→ 把更外一圈也清掉后 **100% 长进去**。
- 剩下 1924 处真·地没清 → 清掉挡路 3 格后：**1918 处（99.7%）立刻长进去**、3 处改道（环在别处长大）、3 处需再清一圈。
- 副作用检查：长出来的环**非法 0 次**（每格度数仍为 2、无重复）。
→ 结论：**选项 1 的论断成立** —— 铁轨停住不长的原因确实只是那几格还是废墟，清了就长（不依赖截图，独立于像素取证）。

- 地形：与当前这局几乎一致（仅 r9 有 2 格差异：(4,9)、(9,9)）。

- **决定性事实：那 26 格当前【全是空白，一个废墟都不挡】。** → 不是"清得不够"。

### 根因一：建模方式根本不同（不是调参能解决）
现行 `recomputeRails` = ① 取「包含镇中心的最大合法**矩形环**」（此处 c4-c7×r5-r8）
→ ② 反复「**整段直边外推一格 + 两端补台阶**」。形状语言只有"矩形 + 台阶凸起"。
往北长必须把 r5 边（c4..c7）整段+两端一起抬起，而 `(4,4)` 是经济建筑、`(6,4)` 是废墟 → **一次都推不动**。
大王的形状（沿空白走廊绕一大圈、右腿 c7 一直到 r0）不在这个语言里。

### 根因二：`ringOk` 的判据过严（反证已证实，脚本 `verify.js`）
- 把大王的 26 格环直接写进 `GS.railPath` 当"上一帧的环" → **被丢弃，退回 12 格矩形**。
- 原因：第 1 步 gate `ringOk(prev)` 要求"每格在**集合层面**恰好 2 个铁轨邻居"；
  该形状有 **8 格集合度数 = 3**（两行铁轨紧贴）：`(6,1)(7,1)(6,2)(7,2)(4,6)(4,7)(7,7)(7,8)`。
- **规律**：只要环的"去腿"和"回腿"落在**相邻两列**，集合层面必然出现度数 3。
  → 现行判据实际上**禁止任何窄于 3 格的环**（内部宽 ≥1），所以永远长不出大王要的窄处折返。
- 但该形状**本身是合法单闭环**：DFS 解出一条 26 格路线（逐格正交、不重复、首尾相接、多边形不自交）。

## 第 11 轮：换模型 —— 外轮廓环 v0.5（state.js 铁轨算法第二次整体替换）

**用户拍板**：「换模型，一定要我给的图里的那种方案」—— 即采用第 10 轮黄金用例（26 格）体现的模型，
放弃「矩形环 + 整段外推」。**本轮改代码，测试全绿。**

### 新模型（`GS.recomputeRails` 整体重写）
铁轨 = **沿「已清空空白连通区 U」的外轮廓走一圈的单线闭环**。步骤：
1. **U**：从镇中心四邻居泛洪，只吃「可铺轨」的格（空白且无建筑）。
2. **洞 F**：被 U 包住但不属于 U、又不碰地图边的连通块（含镇中心建筑本体、被围住的废墟）→ 不铺轨但参与判定。
3. `pruneU` 剪掉 1 格宽死胡同 → 重算 F → 迭代到稳定（`normalize`）。
4. **边界 B = ∂U**：U 中「有一个 4 邻居不在 U∪F」的格。**只收集可铺轨格**（这是修掉「铁轨长在废墟上」的关键）。
5. **补角格 H**：U 中紧邻 B 的格。在 **B（必选）+ H（可选）** 上求**最小补角数的哈密顿环**，且环须**包住镇中心**。
   → 黄金用例正好 **21 格外缘 + 5 格补角 `{(6,2)(5,5)(4,6)(4,7)(7,7)}` = 26 格**，与大王矩阵逐格一致。
   这 5 格补的正是外轮廓在**拐角/回折处的斜跨缺口**，也正是第 10 轮被 ringOk「度数 3」误杀的那 8 格的正当来源。
6. **兜底阶梯**：迷宫状（蛛网）轮廓先 `thinOnce`（削 1 格宽脖颈），再不行 `peelOnce`（剥最外一层），直到可解
   → 表现即「只围最厚实的核心区」，不会摆烂。

### 与旧模型的本质区别
- 旧：「矩形环」是形状语言的全部，只能整段外推 + 两端补台阶 → 窄处回折（两列铁轨紧贴）**原理上做不出来**。
- 新：**先算区域、再沿外缘成环** → 窄处回折是外轮廓的自然产物，不再被判据误杀。
  合法性判据换成「**有序序列**逐格正交相邻且各访问一次」→ 「去腿/回腿落在相邻两列」是合法的。

### 单调性保险（no-shrink）
外轮廓只随清空变大、理论环只增不减。仍加兜底：新环**比上一帧更短**且上一帧仍合法 → **保留上一帧**，避免眼前跳变。

### 扩张提示 `GS.railGrowHints` 与主环**同源**
每格：临时清空 → 走**同一条 `finalRing` 求解链** → 环真的变了才输出（**杜绝空头承诺**）。黄金局实测 5 个：
`(8,1) (8,3) (8,5) (8,6) (3,5)`。

## 第 13 轮：大王补充「铁轨规则 v0.6」（本轮代码零改动，纯评审）

**大王给的 5 条规则**（第 12 轮那三个选项他选了方案 1，并把它细化成规则）：
1. 围住尽可能大的面积；2. 包含镇中心；3. 处处至少 2 格宽；4. 废墟不能有铁轨；5. 同一格只允许十字交叉和单向行驶，不允许同一格往返。

**我的裁决（关键结论，下次直接沿用）**：
- **规则 3 才是真修复，规则 5 不是。** 1 格宽的通道，十字交叉也救不了 —— 通道一格宽，进去必须原路出来，
  永远是「往返」；而十字交叉要求该格有 4 个不同方向的邻格，1 格宽根本给不出。
- **规则 5 等价于「铁轨图必须是欧拉图（每格度数为偶数，且 ≤4）」。** 欧拉回路不允许重复边 → 自动排除度数 1（死端）和度数 3（丁字分支）；
  「往返」正是「重复同一条边」。这个表述比"十字和单向"精确，可直接写进文档。
- ⚠ **【已推翻，见第 13 轮补记】我原本判断「规则 3 成立时十字几乎不会被触发」——错的。** 大王随即给出反例。
  正确结论：**规则 3 和规则 5 是两把平行的刀，各修一类不同的坑，都不冗余**。
- **规则 3 要精确化成「已清空区没有 1 格宽的脖子」**，不能写成"处处 2 格宽"：绕一根 1 格宽的**废墟细墙**是允许的
  （铁轨贴墙两侧走，是两列不同的格，不算往返）；真正致命的是**已清空区**里 1 格宽的通道。写成"处处 2 格宽"会误杀前者。
  换句话：现在的 `thinOnce`（削 1 格宽夹点）要从"兜底阶梯"提到"第一优先"。
- **要补一条规则 6：必须连通（只有一条环）。** 度数全为 2 只保证"每格不往返"，不保证"只有一条环" —— 两个互不相连的方框也满足度数全 2。
- **要补口径**：面积 = 环**内部**格数（环本身不算，废墟算）；并列时先比"用掉的已清空格更多"（贴合玩家清地意图），再比"环更短"（更整齐）。
- **规则 1 是 NP 难度级别的优化问题**，只能"预算内最好"，不是数学最优，要向大王讲清。

**十字交叉的落地代价（重要，别低估）**：现在 `GS.railPath` 是"每格只出现一次的有序序列"（哈密顿回路），
渲染与列车推进（`GS.railCell` / `train.frac`）都按这个写的。要支持十字，同一格得出现两次
→ 必须把输出升级成"**有向边序列 / 欧拉回路**"，渲染要画十字轨、列车推进要按边而不是按格。属结构性改动。
→ 我的建议：**分两步**，先只做规则 1+2+3（+4 + 精确化的 5），不动 railPath 结构；十字留作后续逃生阀。

### 第 13 轮补记（当晚）：大王给出反例，十字交叉是**必做项**而非可选逃生阀

**大王的反例**：十字交叉是用于下面这种 3×3（`1`=铁轨）：
```
0 1 1
1 1 1
1 1 0
```

**脚本 `cross.js` 验证结果（7 格、8 条边、中心格集合度数 = 4）**：
- **哈密顿回路（每格只走一次）条数 = 0，不存在。** 原因：每格只走一次要求每格恰好贡献 2 条边，
  中心格有 4 个铁轨邻居（上/下/左/右都接了轨），只能保留 2 条腿，剩下两条腿的两个格子再也接不回环上。
- **欧拉回路存在**：`(2,0)→(1,0)→(1,1)→(0,1)→(0,2)→(1,2)→(1,1)→(2,1)→(2,0)`。
  中心格被走两次（一次竖穿、一次横穿），每条边恰好一次。**7 格全覆盖、首尾相接、每步正交。**

**概念纠正**：
- "欧拉图解释不了这种"——其实**能**解释（上面那条路就是欧拉回路）。**解释不了它的是"哈密顿回路"**，
  也就是当前 `state.js` 里 `hamCycle` 的模型。所以规则 5 的写法（允许度数 4）本来没错，
  错的是我判断"它很少会被用到"。**十字交叉是必需的。**
- **三个坑、三把刀（平行，不冗余）**：
  1. **1 格宽脖子** → 进去只能原路出来（往返）→ 靠**规则 3** 削掉；
  2. **1 格台阶的 45° 斜切角**（上面这个 `011/111/110`）→ 中心格是两条腿的共用拐点、必须走两遍 → 靠**规则 5 的十字**；
  3. **度数 1 / 3**（死端、丁字）→ 单一闭环永远不会有 → 自动排除，不用特意禁。

**对实现的影响（结论翻转）**：十字从「可选逃生阀」变成**必做项**（45° 斜切角在地图上很常见，任何 1 格台阶的斜边都会产生它）。
→ `GS.railPath` 必须从"每格只出现一次的有序序列（哈密顿）"升级成"**有向边序列（欧拉回路）**"；
渲染要画十字轨（两条线交叉，不能画成两段重叠）；列车到十字格按**直行**（从进入方向的对面出去）——十字格的两条线是 N-S 与 E-W 两条独立通路，
所以不需要岔路/寻路逻辑，是确定性的。
→ 目标函数应加"**最少十字数**"：优先用干净外轮廓，实在不行才用十字。

**待大王拍板**：一次做到位（规则 1+2+3+5 含十字）还是分两步（我现在的建议已改为**直接一次做到位**，
否则 45° 斜切角上仍会削/摆烂，等于白做一轮）。

**待大王拍板**：① 十字交叉现在就做还是先留着（我推荐先留着）；② 面积并列的 tiebreak 口径可否。

## 第 14 轮：铁轨规则 v0.6 落地（欧拉回路 + 削脖子提前）—— state.js 第三次整体重写

### 核心洞察（本轮最值钱的两条）

1. **`railPath` 的语义不用变！** 只要它仍是「有序序列、相邻格严格正交、首尾相接」，
   只是把"每格只出现一次"放宽成"每格最多出现两次（= 十字）"，那么
   `renderer.js`（逐格 `lineTo` 折线）与 `engine.js`（`railCell`/`trainPos`/`trainAngle` 按格心插值）
   **一行都不用改** —— 十字会自然画成交叉。
   → 实测确认（`diag8.js`）：20 段整格线、**0 斜线**；列车 160 个采样点 **0 偏离轨道 / 0 非正交**；
   十字格两次经过都是"直穿对面"（进 1,0 出 -1,0；进 0,1 出 0,-1），确定性、无需岔路寻路。

2. **"1 格宽脖子"的正确定义 = 「U 邻居恰好 2 个」AND「割点」**，两条缺一不可：
   - 只看"邻居恰好 2 个" → 把 2×2 方块里的格误杀（删掉后剩 3 格照样连通）；
   - 只看"割点" → 把大王那个 `011/111/110` 的中心格误杀（它确实是割点，但有 4 个 U 邻居，
     属于规则 5 的十字情形，该由欧拉回路处理，不该被规则 3 削掉）。
   → **这是本轮踩的最大的坑**：第一版只写了"割点"判据，会把需要十字的形状提前削掉。
   ⚠ 另外 `pruneU` 必须**只数 U 邻居**（洞 F 格不能铺轨，不能算作"有出路"）。
   实测对黄金用例两种语义结果完全相同（|U|=31 |F|=2 |B|=21 |H|=9），所以这个改动是安全的。

### 新求解器 `closedTrail`（替换 `hamCycle`）

在 A = B ∪ H 上找闭合迹：覆盖所有 B / 每条边最多走一次 / 每格最多访问 maxVisit 次 /
H 格 ≤ kmax / 访问两次的格 ≤ xmax。分层：`kmax` 从 0 起，同一 kmax 下先试 maxVisit=1（0 十字），
无解才试 maxVisit=2 + xmax=6。这就是"最小十字数"的落地方式。
- 边用 id 表（`eidOf`）标记是否走过 —— **不重复边 = 不允许往返**。
- 起点只作为"终点"出现一次（`w === start` 且 `needLeft===0` 才闭合），避免 start 被计入 maxVisit。
- 三道剪枝：未访问 B 格的连通性 / 起点可达 / 每个未访问 B 格至少还有一条能走的边。

### 五、推荐改法：兜底从「剥层」改成「容差阶梯」（已实测有效）

- `tol > 0` 时关掉「剪枝 C」（只提速用，不影响正确性）

## 回合 16（2026-09-20）：试了「换算法」，结论——不换

**动机**：大王问「tol 加到 40 也见底 10.8%，那换算法行不行？」→ 于是真做了一版**完全不同的算法**（不再靠 DFS 搜索）

3. `(6,9)` 在 A 里也只有 3 条可用边 → 也必须弃一条 → 弃掉只能落在主环上，级联下去同样矛盾。
4. ⇒ 该边是**割边（独木桥）**：走了违奇偶、不走就断两半。**覆盖全 14 格的单条闭环不存在。** ∎

- 铁轨问题 ≡ **一笔画（欧拉回路）**：闭环 ⟺ 连通 + 每格度数偶数（**充要条件**）。
- 网格格最多 4 邻居 → 边界"台阶/凹角"格可用边数是**奇数（1 或 3）**→ 被迫少走一条 →
  当唯一自洽选择恰好是切断**割边**时，环被撕成两半 → **几何上不存在解**。
- 地形是**玩家清出来的**，所以游戏输入空间必然含"清出来就无解"的形状。**再强的算法也变不出一条几何上不存在的环。**
- 出路唯一：**放松约束**（容差阶梯 = 允许少数轮廓格不铺）。

**方法备忘（本轮新增，很有复用价值）**

### 三、根因
`closedTrail` = 「沿轮廓走一圈、中途不许分叉」的 DFS。该盘面轮廓 32 格、多处凹角，

**不是几何无解，是算法选错了。**

### 四、⭐ 本轮最大的坑：圈基的"异或"必须**真异或**
第一版枚举出的 `bestCov=21`（对），但 Hierholzer 走出的 walk 首尾不闭合（38 vs 39）。
探针打出：选中子图 **32 边 / 28 点 / 8 个奇度点**。
**原因：基本圈之间会共用生成树的边**，"置 1 / 置 0"的写法在共用边上退化成**并集**而不是异或：

```js
// ❌ 并集：第二条圈"置 1"是空操作，回溯却把边置 0 → 边集不是任何子集的异或 → 出现奇度点
inE[ke] = 1; deg[EA[ke]]++; deg[EB[ke]]++;
// ✅ 真异或：异或的逆运算就是它自己，回溯再异或一次即还原
if (inE[ke]) { inE[ke] = 0; deg[EA[ke]]--; deg[EB[ke]]--; }
else         { inE[ke] = 1; deg[EA[ke]]++; deg[EB[ke]]++; }
```
改对后：奇度点 **0**、walk 闭合、26 格大环。另在 `fullCheck` 补一道便宜自检：**出现奇度点直接判废**。
> ⚠️ 同样的"并集"写法也在 `feasible.js`/`bench37.js`/`rankstat.js` 里 → 那几份探针报的"最优覆盖率"偏乐观。
